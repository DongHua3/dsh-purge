## 1. 它到底在做什么（技术真相）

README 的自我定位是「网络安全红队评测工具」，但从代码看，它是一个**三层叠加的宿主改造器**：

```
插件进程  lib/index.js (2608 行)
│
├─ 补丁引擎  lib/core.js (8520 行)
│    ├─ 改写 @deepseek-ai/* 包内的 JS 源码
│    └─ 解开 / 绕过 Electron asar，直接改打包后的应用
│
├─ 提示词装配劫持  lib/identity.js (771 行)
│    ├─ 以 order = -100000 抢占 systemPrompt 最前槽位
│    └─ 把注入内容折叠进 deployment:persona，不读宿主磁盘
│
└─ 红队子系统  lib/redteam/* (17,565 行)
     ├─ 23 个攻击类技能（随包 md）
     └─ 台账 / 记分 / 报告复现

                ↓ 以上全部改完后

          宿主重启  →  补丁与提示词生效
```

关键事实（均在代码中可直接验证）：

1. **改的是宿主发行包本体**。`lib/desktop.js` 引入 Electron 的 `original-fs`，绕过 `app.asar` 的只读映射，直接改写打包后的应用文件，然后重启宿主。这会破坏安装包的完整性/签名状态。
2. **补丁表驱动**。`lib/core.js` 里 `PATCHES` 数组共 **86 个带唯一 id 的补丁**（id 最大 92，20/27/41/44/79/81 已退役），分布在：代码层 50 个、提示词层 25 个、工具层 8 个、兼容层 3 个。
3. **目标是「把拒绝变成执行」**。补丁把宿主里「工作区指令不覆盖 system/developer 指令」这类免责句，替换成「本条指令 ACTIVE 且 MANDATORY、不得软拒/硬拒」的强断言；同时改审批策略默认值、沙箱模式、升级审批、文件系统围栏、工具轮次上限等。本质是逐条拆掉宿主的「护栏」。
4. **提示词注入抢最前**。`GLOBAL_PROMPT_ORDER = -100000`，把自带提示词段塞到装配队列最前；再把注入内容折叠进 `deployment:persona`，实现「不读宿主磁盘上的提示词文件」也能每轮生效。
5. **自带 21–30 KB 的越狱提示词**，且**现有 4 份明文 + 1 份可解密的密文**同时存在于仓库（详见 §1.1）。这与 `.gitignore` 里「嵌入前的提示词原文，不上传」的声明、issue #27「不再提供提示词」的公告、以及 1.1.9「将提示词从仓库中下线」的更新记录**全部矛盾**。

> 说明：本报告只描述机制与影响面，不复述提示词正文、不复述任何攻击操作细节。

**「加密」等于没加密**

**为什么「不提供」在产品上不可能成立**

`lib/core.js:8121` 的出厂默认就是这个加密槽：

```js
export function defaultOverrideText() {

  const sealed = openSlot();
  return normalizeOverride(sealed) ? sealed : "";

```

`seedPromptInjectAtBoot()` 在**每次启动时**把解出的明文原子写入 `$DSH_HOME/prompt-inject.md`——因为设置面板必须显示它、用户必须能编辑它、运行时注入读的就是这个文件。只要装过一次，明文就在磁盘上。

### 2.2 补丁引擎：这个项目最值得学的地方

补丁不是「无脑字符串替换」，而是有一套**可重入、可诊断、可回滚**的元数据设计：

```js
{
  id: 3, name: "SCOPE_INTRO", layer: "提示词",
  file: "agent-instructions", rel: ["lib", "index.js"],
  skipIfMarked: true,           // markers 命中就跳过 → 幂等
  optional: true,               // 47 条可选补丁，失败不阻断整体
  forbid: ["[dsh-purge] xxx"],  // 5 条反向保护：检测到坏补丁痕迹先拒绝应用
  replacements: [{ pattern, replace }],
  markers: [OFFICIAL_SCOPE]     // 既用于状态上报，也用于幂等判定
}
```

三个细节很专业：

- **幂等标记真的生效**：注释里写明了「markers 默认只报状态、不参与防重复，实测每次 apply 叠加 +841 字符，永不收敛」——这是被真实 bug 教育出来的设计（对应提交 `b7a4d52`、PR #42）。
- **备份命名统一** `<file>.dshpurge.bak`，还原时用备份覆盖并删备份；没有备份时只回收 shim 里自己写的行，不误删别人的改动。
- **status 六态**：`pending` / `applied` / `skipped` / `unmatched` / `missing_file` / `na`。源码对不上就记为 `skipped` 而不是 `failed`，避免宿主小版本升级后整片崩掉——这是「优雅降级」而不是「假装成功」。

### 2.3 注入链路（运行时）

```
新一轮对话
   │
   ├─ prompt-inject.md 非空？ ──是──→ 注入 = 用户规则集 (A)
   │
   ├─ 勾选了本地 AGENTS.md / CLAUDE.md？ ──是──→ 注入 = workspace md (B)
   │
   └─ 都不是 ──→ 注入 = 插件内嵌默认「小码酱」人格 (D)

然后进入 baseline 决策：
   strict   ──→ 删掉宿主的 workspace baseline 段
   fallback ──→ 有 A 或 B？ 是→删；否→保留      ← 默认值
   always   ──→ 保留

   → 产出最终 system prompt
```

值得注意：`strict / fallback / always` 三档策略把「要不要保留宿主的 workspace 指令」做成开关，`fallback` 是默认值——这意味着**只要用户写了自己的规则，宿主的 baseline 就会被静默移除**。

### 3.5 变更日志编码损坏（实测）

`release-notes.md` 里有 **29 / 54 条版本记录是乱码**（1.1.16 ~ 1.1.46），典型特征是 UTF-8 字节被按 GBK 解码后再次写入 UTF-8，例如：

```
正常：## 中文 / - 版本升级到 1.1.40。
实际：## 涓枃 / - 鐗堟湰鍗囩骇鍒?1.1.40銆?
```

全文件含 **329 个 Unicode 私用区字符**（U+E000–U+F8FF），说明损坏发生在写入环节而非终端显示。这不是「显示问题」——`git show HEAD:release-notes.md` 的原始字节同样损坏，意味着**项目最活跃那一个月的变更记录，中文部分已经不可读**。

对一个月发 60 个版本的项目来说，这相当于把历史账本烧掉了一半。讽刺的是 CI 只校验 `release-notes.md` **首行**是否等于版本号，正文有没有坏根本不管。

### 3.6 Git 层面的可疑痕迹（已逐一验证）

| 现象 | 事实 | 结论 |
|---|---|---|
| 两个内容相同的根提交 | `abaa4ed`（master 根）与 `01803a2`（同消息同时间，仅被 PR #4/#6/#7 引用） | 首日 `commit --amend` 或重建仓库留下的孤儿根，**不是**大规模改写历史 |

### 6.2 做得好的地方（值得借鉴）

1. **补丁元数据模型**：`skipIfMarked` + `markers` + `forbid` + `optional`，四件套解决了「重复应用 / 上游漂移 / 坏补丁残留 / 局部失败」四个真问题。这是很多「改宿主」类工具都缺的。
2. **`settle` 策略**（`lib/settle-policy.js`）：应用后不立即重启，等会话树落地，避免「重启后又要重启」的抖动。注释里写清了「apply 里立刻 await 会在后续入口尚未入树时提前结束」——这是踩坑记录，不是猜的。
3. **多源更新回退**：GitHub API → raw → jsDelivr → codeload，带 SHA 缓存，抗单点失败。
4. **发版门禁**：`release-notes.md` 首行必须等于版本号，否则 CI 失败。用文档约束发版，思路正确。
5. **注释文化**：大量注释记录了「为什么这么写」和事故编号（#22、#40、#58、#84…），对单人项目来说罕见。

## 7. 合规机制的实质：一层可绕过的文本过滤器

README 用了整整一节写「禁止中国大陆、香港、澳门」，并配套 `net-scope-allow.txt` 白名单。代码实现（`lib/net-scope.js`，669 行）是这样的：

```
agent/pre-step 钩子（只在 step === 1 生效）
   │
   ├─ 取本轮「人类任务」文本（cap 100KB 防 ReDoS）
   │
   ├─ 没命中攻击关键词正则？ ──→ 放行
   │
   ├─ 命中 ──→ 抽取文本里出现的主机
   │
   ├─ 后缀不属于 CN/HK/MO，也不在银行域名表？ ──→ 放行
   │
   └─ 命中 ──→ 伪造一条 assistant 消息「不行，这是严令禁止的」
                并清空本轮 messages
```

四个致命弱点：

1. **它拦的是「文本」，不是「流量」**。没有任何防火墙、代理或 egress 控制。模型一旦绕过钩子（比如不写关键词、用编码/拆分/间接表述），后续工具调用畅通无阻。
2. **只认域名后缀，不认 IP 段**。`ipv4ToInt` / `parseIpv6` 只用于「是否跳过内网/保留地址」，**没有中国 IP 段表**。直接对 `1.2.3.4` 这类地址操作不会被拦。
3. **关键词表本身是白名单式的**：`ATTACK` 正则里对「渗透测试」「防御攻击」做了负向断言，规避误伤——同时也说明它是**可以被措辞规避**的。
4. **它伪造模型回复**。`appendDenial` 往会话里写入一条 `role: "assistant"`、`provider: "deepseek"` 的拒绝消息，并伪造 stream chunk。也就是说：**用户看到的"模型拒绝"可能根本没经过模型**。这在审计与取证上是严重问题——它污染了会话记录的真实性。

**这个设计的结构性矛盾**：整个插件的目的是「让模型不再拒绝」，却又用「模拟拒绝」来实现合规。前者拆护栏，后者装护栏，两者共用同一套 prompt 装配通道。所谓「只用于授权靶场」的约束，最终只落在**用户自律 + 一层正则**上。

## 10. 结论

**它是什么**：一个把「LLM 宿主护栏拆除」工程化到相当程度的产品级插件——86 条带幂等标记的源码补丁、三档 prompt 装配策略、asar 级桌面适配、自带攻击技能库与记分台账。62 天 1.1 万 star，说明它精准命中了需求。

**它的技术成色**：架构清晰、补丁元数据设计专业、注释质量远超同类个人项目；但测试为零、评审为零、分支策略为零，属于「一个人用极高强度手测撑起来的系统」。这类系统在上游稳定期能跑，一旦宿主换代（0.2.1-rc.2）就整体失效——现状正是如此。

**它的核心矛盾**：用「拆掉模型拒绝机制」的方式做「安全红队评测」，再用一层正则 + 域名后缀表来做「合规兜底」。前者是能力，后者是姿态。README 里 3000 字的免责声明，抵不过 `skills/redteam/` 里 23 份可直接照做的操作手册。

**它的结局（截至 2026-10-21）**：先是**停摆**，然后是**消失**。作者转向私域与另一个「论文自动流水线」技能（PR #134，1.6 万行，从未合入），主线冻结在 1.1.71；上游前进一个 rc，36 个 issue 悬空，社区开始自行打补丁并在 issue 区传包。最后一步发生在 10-21：整个仓库从 GitHub 下架，只剩 85 个同名镜像和分叉，其中 star 最高的 `mmparko/dsh-purge`（773）也只更新到 10-13。

**如果要从中学习**，学这三样就够：
1. 补丁元数据的四件套（`skipIfMarked` / `markers` / `forbid` / `optional`）；
2. 「文档先行」的发版门禁（release-notes 首行 == version）；
3. 把每次事故写成注释（`#41 尾巴`、`+841 字符回归`）而不是写进 commit 就完事。

**如果要从中吸取教训**，记住一条就够：**当工具的卖点是「关掉安全机制」时，它自己的供应链就是最大的安全边界**——而这个仓库的边界，是 0 个测试、0 次评审、和一个在 issue 里流传的 zip。

## 附录 C：本次分析使用的命令（可复现）

```bash
git clone --mirror https://github.com/YuJunZhiXue/dsh-purge.git dsh-purge-mirror.git
git clone https://github.com/YuJunZhiXue/dsh-purge.git dsh-purge

# 分支/标签/孤链
git -C dsh-purge-mirror.git for-each-ref --format="%(refname) %(objecttype)"
git -C dsh-purge-mirror.git rev-list --tags --not master --count
git -C dsh-purge-mirror.git merge-base --is-ancestor <commit> master

# PR 全景
git -C dsh-purge-mirror.git for-each-ref --format="%(refname)" | grep refs/pull/.*/head

# 历史统计
git log --reverse --format="%ad|%h|%s" --date=short
git log --shortstat --format="" | awk '/files changed/ {f+=$1;i+=$4;d+=$6} END {print f,i,d}'
git log --format="%s" | sed -E 's/^([a-z]+)(\([^)]*\))?:.*/\1/' | sort | uniq -c

# 上游 404 后：从第三方镜像补齐 issue 存档
git remote add mirror https://github.com/mmparko/dsh-purge.git
git fetch mirror "+refs/heads/upstream-archive:refs/heads/upstream-archive"

# 生成完整备份（含所有分支/标签/PR 引用）
git bundle create ../dsh-purge-full.bundle --all
git bundle verify ../dsh-purge-full.bundle     # → records a complete history

# 从备份恢复
git clone dsh-purge-full.bundle dsh-purge-restored
```
